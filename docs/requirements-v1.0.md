# 1. プロジェクト概要

## 1.1 プロジェクトの目的

複数のユーザーが同一のドキュメントを同時に編集できる、リアルタイム共同編集APIを開発する。

Google Docsのように、複数人が同じ文章を同時に編集しても、編集内容が矛盾なく統合され、すべてのクライアントで整合性の取れた状態になるシステムを目指す。

単なる文章共有アプリではなく、外部の開発者が自分のアプリケーションに組み込める汎用的な共同編集基盤として開発する。

最終的には以下を実現する。

- 複数ユーザーによる同時編集
- 編集内容のリアルタイム同期
- 編集競合の自動解決
- オフライン編集
- 再接続時の変更統合
- 編集履歴の保存
- 過去状態への復元
- 複数サーバー間の同期
- 外部開発者向けAPI公開
- 将来的なSDK提供

## 1.2 プロジェクトの基本方針

以下の3点は決定事項である。

1. CRDTはYjsを利用して実用的な共同編集システムを完成させた後、独自CRDTを実装する。
2. APIだけでなく、実際に共同編集できるWebアプリケーションも開発する。
3. 開発環境はローカル環境で構築し、完成後にクラウドへ公開する。

開発では、実用性と技術的理解の両方を重視する。

既存ライブラリを利用して完成させるだけでなく、内部の仕組みを理解し、将来的には独自実装と比較検証できる構造にする。

# 2. 開発対象

本プロジェクトは以下の4領域で構成する。

2.1 フロントエンド
ユーザーが操作するWeb共同編集アプリケーション。

2.2 REST APIサーバー
ユーザー認証、ドキュメント管理、権限管理などを担当する。

2.3 Collaboration Server
WebSocket通信、CRDT処理、編集差分の同期、接続管理を担当する。

2.4 Persistence Layer
編集更新、スナップショット、バージョン、ユーザー情報などを永続化する。

各領域は責務を分離し、将来的に独立したサーバーへ分割できる構造にする。

初期段階ではREST APIとCollaboration Serverを同一プロセスで起動してもよい。ただし、内部モジュールは分離する。

3.1 Owner

- ドキュメントの編集

- メンバーの権限変更
- ドキュメントの削除
- 編集履歴の閲覧
- 過去バージョンへの復元

3.2 Editor
- ドキュメントの閲覧
- ドキュメントの編集
- 編集履歴の閲覧

3.3 Viewer
- ドキュメントの閲覧
- 編集履歴の閲覧

WebSocket接続時だけでなく、接続中も権限変更を反映する。

Viewerによる編集操作はサーバー側で拒否する。

# 4. 機能要件

## 4.1 ユーザー管理

- ユーザー登録
- ログイン
- ログアウト
- 認証トークンの発行
- 認証トークンの更新
- ユーザー情報の取得

認証方式はJWTとRefresh Tokenを第一候補とする。

パスワードは安全なハッシュアルゴリズムで保存する。

## 4.2 ドキュメント管理

- ドキュメント作成
- ドキュメント取得
- ドキュメント一覧取得
- ドキュメント情報更新
- ドキュメント削除
- メンバー追加
- メンバー削除
- メンバー一覧取得
- メンバー権限変更

## 4.3 リアルタイム共同編集

以下の操作に対応する。

- 文字の挿入
- 文字の削除
- 範囲選択
- テキスト置換
- リッチテキスト編集
- 見出し
- 箇条書き
- 番号付きリスト
- 太字
- 斜体
- 他ユーザーのカーソル表示
- 他ユーザーの選択範囲表示
- 編集中ユーザー一覧表示

複数ユーザーの編集内容はリアルタイムに同期する。

## 4.4 編集競合の解決

本システムの最重要機能。

以下の状況に対応する。

- 同じ位置への同時挿入
- 同じ範囲への同時削除
- 挿入と削除の競合
- 複数ユーザーによる同時置換
- 異なる順番で到着した更新
- 同一更新の重複配信
- 通信遅延による更新順序の逆転

すべてのクライアントが同じ更新集合を受信した場合、最終的に同じドキュメント状態へ収束すること。

単純な最終文章の上書き方式は採用しない。

## 4.5 オフライン編集

- ネットワーク切断中も編集できる。
- 編集内容をブラウザのIndexedDBへ保存する。
- 未送信の編集更新を保持する。
- 再接続時にサーバーと同期する。
- オフライン中の編集内容とサーバー側の編集内容を統合する。
- 重複更新を防止する。
- 同期状態をユーザーに表示する。

再接続時はState Vectorを利用した差分同期を基本とする。

## 4.6 編集履歴

- 編集更新の保存
- 操作者の記録
- 編集日時の記録
- 編集履歴の取得
- スナップショットの生成
- バージョン管理
- 過去状態の参照
- 過去状態への復元

CRDTの更新ログと監査ログは目的が異なるため、別々に管理する。

復元時は過去の状態を直接上書きするのではなく、復元対象の状態を新しい編集状態として反映する。

## 4.7 接続管理

- WebSocket接続
- 接続ユーザー管理
- 切断検知
- 自動再接続
- ハートビート
- セッション管理
- 不正接続の拒否
- 複数サーバー間のイベント配信

# 6. CRDTエンジン設計

## 6.1 基本方針

Yjsを採用し、実用的な共同編集システムを先に完成させる。

その後、独自CRDTを実装する。

Yjsと独自CRDTを交換可能にするため、CRDTエンジンを独立したモジュールとして設計する。

## 6.2 共通インターフェース

以下を設計の基準とする。

```ts
interface CRDTEngine {
  createDocument(): CollaborativeDocument;

  applyUpdate(
    document: CollaborativeDocument,
    update: Uint8Array
  ): void;

  encodeState(
    document: CollaborativeDocument
  ): Uint8Array;

  encodeStateVector(
    document: CollaborativeDocument
  ): Uint8Array;

  getStateDiff(
    document: CollaborativeDocument,
    stateVector: Uint8Array
  ): Uint8Array;
}
```

これは設計イメージであり、実装時には型の詳細や非同期処理の必要性を検討する。

## 6.3 エンジン構成

```
CRDTEngine
├── YjsEngine
└── CustomCRDTEngine
```

CustomCRDTEngineは後続フェーズで開発する。

Yjs内部のデータ形式と独自CRDTのデータ形式は異なるため、共通インターフェースを介して扱う。

## 6.4 Yjsのデータ構造

初期版ではTiptapとの連携を考慮し、Y.XmlFragmentを採用する。

文書メタデータにはY.Mapを利用する。

文書の本文とメタデータは責務を分離する。

# 7. WebSocket通信仕様

## 7.1 接続先

wss://api.example.com/ws/documents/{documentId}

## 7.2 接続時の処理

1. JWT検証
2. ユーザー確認
3. ドキュメント確認
4. ドキュメントへの参加権限確認
5. セッション生成
6. 初期同期

## 7.3 イベント

以下のイベントを基本とする。

- sync:request
- sync:response
- update:submit
- update:broadcast
- update:ack
- awareness:update
- document:user_joined
- document:user_left
- sync:complete
- error

## 7.4 更新メッセージ

初期版ではJSON形式のエンベロープを採用する。

```json
{
  "type": "update:submit",
  "updateId": "upd_001",
  "payload": "BASE64_DATA"
}
```

payloadにはCRDT更新データを格納する。

将来的にはバイナリフレームへの移行を検討する。

## 7.5 データの分類

文書更新とAwareness情報は分離する。

文書更新：
- 永続化対象
- 編集履歴管理対象
- 再接続時の同期対象

Awareness：
- カーソル位置
- 選択範囲
- オンライン状態
- 一時的なユーザー情報

Awarenessは基本的に永続化しない。

## 7.6 更新処理の順序

1. 更新受信
2. 認証・権限検証
3. 更新サイズ・形式検証
4. 重複確認
5. CRDT更新の検証・適用
6. PostgreSQLへの保存
7. トランザクションCommit
8. ACK返却
9. 他ユーザーへの配信

DB保存に失敗した更新は成功扱いにしない。

ACKは永続化完了後に返す。

配信失敗時は再接続時の同期で回復できるようにする。

将来的にOutboxパターンを導入し、DB保存とイベント配信の整合性を高める。

# 11. オフライン同期設計

IndexedDBを利用し、クライアント側に文書状態を保持する。

候補ライブラリ：
- y-indexeddb

基本処理：

1. 編集操作をローカルY.Docに反映する。
2. IndexedDBへ保存する。
3. オンラインならサーバーへ送信する。
4. オフラインなら送信を保留する。
5. 再接続時にState Vectorを交換する。
6. 不足している差分を取得する。
7. 未送信の更新を送信する。
8. サーバーの永続化ACKを確認する。
9. 同期完了を通知する。

ローカル更新はサーバーで永続化されたことを確認する前に削除してはならない。

# 15. テスト要件

以下のテストを実施する。

- CT-01：2人同時編集 — 両方の変更が残ること。
- CT-02：同一箇所への同時挿入 — 全クライアントの状態が一致すること。
- CT-03：同時削除 — 不整合が発生しないこと。
- CT-04：更新順序の逆転 — 最終的に全クライアントが収束すること。
- CT-05：重複更新 — 二重反映されないこと。
- CT-06：オフライン編集 — 再接続後に変更が統合されること。
- CT-07：サーバー再起動 — 保存済み状態を復元できること。
- CT-08：権限違反 — 編集権限のないユーザーの更新を拒否すること。
- CT-09：大量接続 — 規定性能を満たすこと。
- CT-10：履歴復元 — 指定バージョンの状態を復元できること。

Property-based Testingを導入し、ランダムな操作列でも状態収束を検証する。

# 19. 開発時のAIへの指示

本プロジェクトを実装するAIは以下の方針に従うこと。

1. 要件定義書を基準として開発する。
2. 要件にない機能を勝手に追加しない。
3. 未決定事項は推奨案を提示し、決定事項と区別する。
4. 技術選定の理由を説明する。
5. 設計上の問題やリスクを発見した場合は、実装前に報告する。
6. 既存のコード構成や設計思想を確認してから変更する。
7. 実装した機能には自動テストを用意する。
8. テストを実行し、実際の結果を報告する。
9. 未検証の機能を完成済みと報告しない。
10. 重要な設計変更はADRに記録する。
11. セキュリティやデータ消失のリスクを軽視しない。
12. 一度に大量のコードを生成するのではなく、小さな単位で実装・検証を繰り返す。

重大なリスク、不可逆操作、費用発生、外部へのデータ送信については事前に確認する。

技術的な詳細については、合理的な推奨案を自律的に提示してよい。

# 20. 最初の作業指示

まずPhase 0の開発基盤構築から開始すること。

ただし、いきなりファイルを大量生成するのではなく、最初に以下を実施する。

1. 現在の開発環境を確認する。
2. 必要なソフトウェアのインストール状況を確認する。
3. Node.js、pnpm、Git、Dockerのバージョンを確認する。
4. 推奨するMonorepo構成を提示する。
5. ディレクトリ構成を確定する。
6. 必要な依存関係を整理する。
7. Phase 0の実装手順を提示する。
8. 小さな単位で構築・起動・テストを行う。

最初の目標は、ローカル環境でReact、Fastify、PostgreSQLが連携して正常に動作する開発基盤を完成させることである。
