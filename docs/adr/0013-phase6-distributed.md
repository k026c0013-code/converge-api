# ADR-0013: Phase 6 の分散化（Redis・複数 Collaboration Server・負荷分散・障害復旧・負荷試験）

- 状態: 採用（2026-11-23〜24、ユーザーが判断を委任「承認なしに進め続けていい」）
- 関連: ADR-0005（チケット）, ADR-0009 §4（イベントバス）, ADR-0010（同期）, レビュー R-13, R-15 / 要件定義書 §4.7, §5.3, §12, §14 Phase 6, §15 CT-09

## 1. 構成
- Redis 7.4 を `compose.yaml` で起動する（`docker compose up -d redis`）。MySQL はホストのまま（ADR-0002）。
- `REDIS_URL` を設定すると複数ノードのモードになる。未設定なら Phase 5 までと同じ単一ノードで動く（`LocalCluster`）。
- 負荷分散は nginx（`docker compose --profile lb up -d`, `infra/nginx.conf`）で、ホストの :3001 と :3002 にラウンドロビンで振り分ける。チケット・在席・更新はすべて Redis で共有するので、**スティッキーセッションは不要**。

## 2. ノード間で共有するもの
| 対象 | 方式 |
|---|---|
| 接続チケット | `SET converge:ticket:{sha256} … PX 30000`、消費は `GETDEL`（どのノードで発行しても使え、1 回限り） |
| 権限変更・ログアウト（R-13） | Pub/Sub `converge:access`。ローカルの `AccessEvents` と橋渡しする（受け取ったものは再送しない） |
| 文書更新・awareness・参加/退出 | Pub/Sub `converge:docs`。更新は**保存したノードだけが発行**し、他のノードはライブ文書に適用して自分の接続へ配信する |
| 在席（参加者一覧） | ハッシュ `converge:presence:{documentId}`。値にノード ID を持つ |
| ノードの生存 | `converge:node:{id}`（TTL 15 秒、5 秒ごとに更新） |

## 3. 取りこぼしと障害への対策
- **Pub/Sub は最大 1 回の配送**で、取りこぼしうる。そこで各ノードは、接続がある文書について **5 秒ごとに DB から直近の更新 ID を読み**、まだ適用していないものだけを取り込んで配信する（キャッチアップ）。Redis が再接続したときも、すぐ同じ処理をする。
  - 適用済みの ID はノードごとに覚えておく。本文を読むのは未適用の分だけ。
  - 二重に適用しても、Yjs の冪等性で結果は変わらない。
- **ノードが落ちた場合**: クライアントは自動で再接続し、ロードバランサーが生きているノードへ振る。状態は DB から復元する（CT-07 と同じ）。落ちたノードの参加者は、生存キーの期限が切れた時点で他のノードが在席ハッシュから消し、`document:user_left` と awareness の削除を配信する。

## 4. 設定の追加
- `RATE_LIMIT_GLOBAL` / `RATE_LIMIT_AUTH` / `RATE_LIMIT_MEMBER_ADD`（毎分の回数）。既定値は ADR-0008 のまま。負荷試験のときだけ引き上げる。
- `COLLAB_TIMING=1`: 更新処理の各段階（キュー待ち・INSERT・受信から ACK まで・イベントループの遅延）の p50/p95 を 10 秒ごとにログへ出す。既定は無効。

## 5. 負荷試験の結果（CT-09、2026-11-24、ローカルの Windows 11 / Core Ultra 5 135H / MySQL 8.0）
条件: 100 接続、5 文書 × 20 人が、各自 1 秒に 1 回編集する。30 秒間、2 ノードに分散。

| 経路・クライアント | ACK P95 | 反映 P95 | エラー |
|---|---|---|---|
| Node クライアント → 2 ノードへ直接 | **65 ms** | **87 ms** | 0 |
| Node クライアント → nginx（Docker Desktop）→ 2 ノード | 324 ms | 337 ms | 0 |
| k6（Docker）→ nginx → 2 ノード | 2.55 s | 2.56 s | 0 |
| REST（k6, 登録・メンバー追加・チケット） | P95 **245 ms** | — | 0 |

- **サーバー自体は目標（反映 P95 200 ms、REST P95 300 ms）を満たす**。サーバー内の内訳（2 ノード時の p95）は、INSERT 約 40 ms、キュー待ち約 30 ms、受信から ACK まで約 62〜76 ms、イベントループの遅延約 15 ms。
- nginx 経由の遅さは、**Windows の Docker Desktop が Windows と WSL VM の間を往復する通信**の影響で、本番環境の値ではない。
- k6 の値は、k6 自身の JavaScript 実行環境が毎秒約 1,800 件の WebSocket メッセージを処理しきれていないことによる（同じ経路の Node クライアントは 324 ms）。k6 は REST の計測と、エラーが 0 件であることの確認に使う。
- 本番に近い計測は、Phase 7 の配置先（Linux）で取り直す。

## 6. 未決定・今後
- 1 文書の更新が 1 ノードに集中する設計（文書ごとの担当ノード）は採らない。全ノードが全文書の Pub/Sub を受け取る。文書数が大きく増えたら、チャンネルを文書ごとに分けることを検討する。
- Redis 自体の冗長化（Sentinel / Cluster）は Phase 7 の配置先と一緒に決める。
