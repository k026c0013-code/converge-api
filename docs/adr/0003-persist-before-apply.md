# ADR-0003: 更新の処理順序を「保存してからライブ文書へ適用」にする

- 状態: 採用（2026-11-23、ユーザーが判断を委任「すべて君の感性に任せる」）
- 関連: レビュー R-02 / 要件定義書 §7.6 / Phase 3

## 背景
§7.6 の順序「CRDT適用 → DB保存 → Commit」では、DB保存に失敗してもサーバーのメモリ上の Y.Doc には反映済みになる。
その後に接続したクライアントは初期同期で「成功扱いにしていない更新」を受け取り、「DB保存に失敗した更新は成功扱いにしない」と矛盾する。

## 決定
1 件の更新を次の順で処理する。

1. 受信・サイズ上限の確認
2. **形式検証**: 一時的な Y.Doc でデコード・適用を試す（ライブ文書には触れない）。検証内容の詳細は R-03 の ADR で決める
3. `document_updates` へ INSERT（`(document_id, update_id)` の重複は `ON DUPLICATE KEY UPDATE id = id` で吸収）
4. Commit
5. ライブ文書（メモリ上の Y.Doc）へ適用
6. 送信者へ ACK
7. 他の接続へ配信

- 重複した `update_id`（再送）は、保存済みとして ACK だけ返す。ライブ文書への再適用と再配信はしない。
- 3〜4 が失敗したら NACK を返す。ライブ文書と他の接続は変化しない。
- 5 が失敗したら（2 を通過していれば通常は起きない）、エラーを記録する。そのうえでライブ文書をメモリから破棄し、次のアクセスで DB から再構築する。DB が正なので、データは失われない。

## 理由
- Yjs の更新は冪等かつ可換なので、適用を保存の後にしても最終状態は同じになる。
- 「メモリにはあるが DB にはない」状態がなくなる。再起動後の状態が配信済みの状態と一致するため、CT-07 が安定する。

## 影響
- 配信は Commit の後になるため、DB の書き込み遅延が編集の反映時間に加わる（R-15）。Phase 3 で計測し、必要ならクライアント側でまとめて送る。
- 要件定義書 §7.6 の手順5・6を本 ADR の順序で読み替える。
