# ADR-0005: WebSocket の認証に短命・1回限りの接続チケットを使う

- 状態: 採用（2026-11-23、ユーザーが判断を委任「すべて君の感性に任せる」）
- 関連: レビュー R-05, R-13 / 要件定義書 §7.2, 未決定事項3 / Phase 2

## 背景
ブラウザの WebSocket API には Authorization ヘッダーを付けられない。JWT をクエリ文字列に入れると、アクセスログやプロキシに長寿命の資格情報が残る。また、接続は長く続くため、途中で JWT が失効する。

## 決定
1. **チケット発行**: クライアントは REST の `POST /documents/{id}/ws-ticket` を JWT 付き（Authorization ヘッダー）で呼ぶ。サーバーはその文書の閲覧権限を確認し、チケットを返す。
   - 中身: 暗号論的乱数 32 バイト（base64url）。
   - 有効期限は **30 秒**で、**1 回限り**。`userId` と `documentId` に結び付ける。
   - サーバーにはハッシュ（SHA-256）だけを保存する。Phase 2〜5 はプロセス内のメモリに置き、Phase 6 で Redis に移す。
2. **接続**: `wss://…/collab?ticket=<チケット>` で接続する。サーバーはハンドシェイク時にチケットを検証して消費し、失敗したら接続を拒否する。
   - Origin ヘッダーを許可リストで確認する（CSWSH 対策）。
   - ログに出す URL ではチケットを伏せ字にする（1回限りでも念のため）。
3. **接続中**:
   - アクセストークン（JWT）が失効しても接続は切らない（認証はハンドシェイクで済んでいる）。
   - 次の場合は、サーバーが接続を切るか、役割の降格を通知する（通知の経路は R-13 の決定に従う）。
     - 権限の変更・削除
     - ログアウト（リフレッシュトークンの失効）
     - ユーザーの削除
   - 接続の最大寿命は **12 時間**とする。過ぎたらサーバーが切断し、クライアントは新しいチケットで再接続する。

## 理由
- クエリ文字列に載るのは 30 秒・1 回限りの値だけになり、漏れても再利用できない。
- 「最初のメッセージで認証する」方式より、未認証の接続を保持する時間がなく、実装も単純。

## 影響
- REST エンドポイントが 1 つ増える（`POST /documents/{id}/ws-ticket`）。認証方式の詳細（未決定事項3）として要件定義書の API 一覧に追加する。
- 複数のサーバー台数で動かす Phase 6 では、チケットの保存先を Redis にする必要がある。
