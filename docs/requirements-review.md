# 要件定義書 v1.0 レビュー（2026-11-23）

対象: `docs/requirements-v1.0.md`
凡例: **[矛盾]** 記述同士が食い違う / **[不足]** 必要な定義がない / **[リスク]** 技術的に難所・破綻しうる
各項目の「推奨案」は **未決定の提案** であり、決定事項ではない。採否はADRで確定する。

影響フェーズ欄の項目は、そのフェーズ着手前に決着させる必要がある。Phase 0 を止める項目は R-01 のみ。

> 追記（同日）: ユーザー指示により DB を MySQL 8.0 に変更（ADR-0002）。R-01 は Phase 0 については解消。R-17 は MySQL の前提で読み替える（重複確認は `ON DUPLICATE KEY UPDATE`、BYTEA→LONGBLOB）。

## A. 重大（設計を変える可能性が高い）

### R-01 [リスク] Docker が未インストール（Phase 0 を止める）
- 現状: Windows 側にも WSL2 Ubuntu 側にも Docker/Compose がない。PostgreSQL もない。
- 推奨案: Docker Desktop（WSL2 backend）を winget で導入（個人利用は無償）。代替は WSL Ubuntu に Docker Engine を入れる（sudo が必要）。
- 影響: Phase 0

### R-02 [矛盾] 7.6 の処理順序「CRDT適用 → DB保存 → Commit」
- 手順5でサーバーのメモリ上 Y.Doc に適用してから手順6で保存すると、DB保存に失敗したとき **メモリ上の文書には反映済みで、DBにはない** 状態になる。その後に接続した別クライアントは初期同期で「成功扱いにしていない更新」を受け取る（「DB保存に失敗した更新は成功扱いにしない」と矛盾）。再起動すると消えるので CT-07 も不安定になる。
- 推奨案: 「形式検証（デコードのみ・ライブ文書には適用しない）→ INSERT → Commit → ライブ文書へ適用 → ACK → 配信」。Yjs の更新は冪等かつ可換なので、後から適用しても結果は同じ。
- 影響: Phase 3

### R-03 [リスク] 「更新データの検証」（13章）を Yjs でどう実現するか未定義
- Yjs の update は「どの共有型をどう変えるか」を任意に表現できる。Editor 権限で、本文以外（メタデータ Y.Map、未知のルート型）への書き込み、巨大な削除・挿入、不正なバイナリ（デコード時例外・メモリ消費）を送れてしまう。
- 推奨案: (1) サイズ上限、(2) サーバー側の一時 Doc でデコード試験、(3) 適用後に許可されたルート名（`content`, `meta`）以外が生えたら拒否、(4) `meta` の書き込みは Owner のみ、などを ADR で規定する。完全な意味検証は困難であることを明記する。
- 影響: Phase 3

### R-04 [矛盾] タイトルの二重管理
- `documents.title`（DB、REST の PATCH で更新）と、6.4 の「メタデータは Y.Map」の両方にタイトルを持つ可能性がある。どちらが正か定義がない。
- 推奨案: タイトルなどの管理情報は DB・REST が正。Y.Map はエディタ内の一時的な共有設定だけにする（または Phase 1 では Y.Map を使わない）。
- 影響: Phase 1 / 3

### R-05 [リスク] ブラウザの WebSocket は Authorization ヘッダーを付けられない
- 7.2 の「接続時のJWT検証」の方法が決まっていない。クエリ文字列に JWT を入れるとアクセスログやプロキシに残る。接続が長く続くと JWT が途中で失効する。
- 推奨案: REST で発行する短命（例: 30秒）・1回限りの接続チケットを `?ticket=` で渡す。または接続直後の最初のメッセージで認証する。接続中のトークン失効と権限変更は、サーバーから切断／役割の降格を通知して扱う。
- 影響: Phase 2（未決定事項3「認証方式の詳細」に該当）

### R-06 [リスク] 独自CRDTへの差し替えはサーバー内部だけでは済まない
- payload は CRDT 固有のバイナリ形式。クライアント（Tiptap + y-prosemirror）も Yjs に依存している。CRDTEngine インターフェースはサーバーしか抽象化しておらず、Phase 7 で外部公開した後に Phase 8 でエンジンを替えると互換性が壊れる。独自CRDT用の ProseMirror バインディングも別途必要になり、作業量が非常に大きい。
- 推奨案: `documents` に `engine`（例: `yjs`/`custom`）と `format_version` を持たせ、エンジンは文書単位で固定する。Phase 8 はまずプレーンテキストに限定し、サーバー側の比較・テスト用にする。
- 影響: Phase 1（カラム追加）/ 8

### R-07 [リスク] 復元（4.6）の実装方式
- 「過去状態を新しい編集として反映」は、Yjs では「現在の内容を全削除し、スナップショットの内容を再挿入する」更新になるのが一般的。復元中に他の人が編集していると、その編集が復元結果に混ざる。他人のカーソルも飛ぶ。Yjs の GC（既定で有効）では過去の削除内容が文書内に残らないため、スナップショットの `state_data` から復元するしかない。
- 推奨案: 復元は Owner のみ。復元の瞬間は文書を短時間ロックするか、混ざりうることを仕様として明記する。CT-10 の期待値（「復元直後の状態が一致」なのか「復元後に並行編集が残る」なのか）を定義する。
- 影響: Phase 5

## B. 不足

### R-08 [不足] REST API の欠落
- 4.2「メンバー権限変更」に対応する `PATCH /documents/{id}/members/{userId}` がない。
- 4.1「ユーザー情報の取得」に対応する `GET /users/me` がない。
- 4.6「過去状態の参照」に対応する `GET /documents/{id}/versions/{versionId}` などがない。バージョンの作成（手動保存）エンドポイントもない。
- メンバー追加の指定方法（メールアドレスか userId か）が未定義。メールアドレスで追加できると、ユーザーの存在確認に悪用されうる。

### R-09 [不足] DB スキーマの欠落
- `refresh_tokens`（失効・ローテーション・ログアウトに必要）がない。
- `audit_logs`（4.6・13章で「別管理」とあるが表がない）がない。
- `users.display_name` がない（カーソル・参加者一覧に表示する名前）。`users.updated_at` もない。
- `document_snapshots` に「どの更新まで含むか」（最後の `document_updates.id` や state vector）がない。スナップショット＋差分で状態を復元できない。
- `document_versions` に名前・メモがない。
- `documents.owner_id` と `document_members.role='owner'` の二重管理。Owner は複数か？ 譲渡は？ 最後の Owner を削除・降格できるか？
- 文書削除が論理削除か物理削除かが未定義（データ消失リスク）。
- `update_id` が 8.4 では UUID、7.4 の例では `"upd_001"`。どちらかに統一する（推奨: クライアントが生成する UUID）。

### R-10 [不足] 「未送信の更新」の定義（4.5 / 11章）
- y-indexeddb は文書全体を保存するだけで、どの更新が送信済みかは記録しない。Yjs の考え方では「未送信」＝「サーバーの state vector との差分」であり、更新を1件ずつ管理するキューとは別物。
- 推奨案: 再接続時に state vector で差分を作り、まとめて1件として送る（新しい updateId を付ける）。二重反映の防止は CRDT の冪等性に任せ、`(document_id, update_id)` のユニーク制約は「同じ送信の再試行」用と役割を分ける。どちらの方式を取るかを ADR で決める。
- 影響: Phase 4

### R-11 [不足] 「テキスト置換」「同時置換」の期待結果
- CRDT では置換は「削除＋挿入」。2人が同じ語を同時に置換すると、**両方の挿入が残る**（例: 「cat」→「dog」「cow」→「dogcow」）。収束はするが、意図した結果にはならない。CT のテストで期待する結果を明記する必要がある。

### R-12 [不足] Awareness のなりすまし
- Awareness の名前・色はクライアントが自分で申告する。他人の名前を名乗れる。
- 推奨案: サーバーが userId と表示名を付与・上書きして配信する。

### R-13 [不足] 接続中の権限変更をどこから通知するか
- REST で権限を変えたことを Collaboration 側へどう伝えるか（同一プロセスなら内部イベント、Phase 6 では Redis Pub/Sub）。権限確認を「接続時のみ」「メッセージごと（キャッシュ＋無効化）」のどちらにするかが未定義。

## C. 計画・非機能のリスク

### R-14 [リスク] Phase 2 と Phase 3 の順序
- CRDT なしで「編集イベント配信」「カーソル共有」を作ると、Phase 3 で捨てるコードになる。Tiptap のカーソル共有は Yjs の Awareness（y-prosemirror）が前提。
- 推奨案: Phase 2 は「中身を解釈しない配信（バイナリ payload をそのまま中継）＋接続・在席管理」に限定し、エディタ連携とカーソルは Phase 3 で行う。

### R-15 [リスク] キー入力ごとの DB コミットと P95 200ms
- 7.6 では配信がコミットの後になるため、DB の書き込み遅延がそのまま編集反映時間に加わる。20人が同時に入力すると、1文書あたり毎秒数十〜百件以上の INSERT になる。
- 推奨案: クライアント側で更新をまとめて送る（例: 50〜100ms 単位）。document_updates は定期的にスナップショットへ圧縮する（未決定事項5・6）。k6 で早めに計測する。

### R-16 [リスク] 独自プロトコルとプロバイダーの自作
- 7.3 のイベント設計は y-websocket や Hocuspocus のプロトコルと互換性がない。そのため、クライアント側の Yjs プロバイダー（同期・Awareness・再接続・ACK 管理）を自作することになる。学習目的としては妥当だが、作業量が大きく、バグも出やすい。
- 推奨案: 自作する前提で、プロバイダーを `packages/client`（将来の SDK の土台）として切り出す。

### R-17 [リスク] Prisma と BYTEA・大量 INSERT
- Prisma は `Bytes` で BYTEA を扱えるが、更新ログのような追記中心の大量書き込みや、`ON CONFLICT DO NOTHING`（重複確認）は `$queryRaw` を使う必要が出る可能性が高い。

### R-18 [不足] ライセンス（未決定事項10）
- Yjs・y-prosemirror・y-indexeddb・Tiptap のコアは MIT。Tiptap の有料機能（Pro 拡張・Tiptap Cloud・一部の協調編集サービス）は使わない方針を明記するとよい。Docker Desktop は組織規模によっては有料になる（個人・教育用途は無償）。

### R-19 [リスク] ブランチ運用
- 1人開発で main/develop/feature の3層は負担が大きい。GitHub へ公開する前は、ローカルで main＋feature ブランチだけを使うことを推奨（決定事項ではないため、現時点では develop ブランチも作成する）。
